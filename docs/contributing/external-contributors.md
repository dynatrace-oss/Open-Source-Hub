# External Contributors

Dynatrace welcomes contributions from external developers, users, partners, customers, maintainers, and members of the broader open source community.

Each public repository should clearly explain how contributions are accepted and what contributors can expect from maintainers.

## Contribution expectations

External contributors should follow the repository's:

- `CONTRIBUTING.md`.
- `CODE_OF_CONDUCT.md`, where applicable.
- Pull request process.
- Testing requirements.
- Documentation requirements.
- CLA or DCO requirements, where applicable.
- Security reporting instructions.

Repository-specific guidance takes precedence over general guidance in the Open Source Hub.

## Types of contributions

Contributions may include:

- Bug reports.
- Documentation improvements.
- Test improvements.
- Code changes.
- Feature proposals.
- Examples.
- Integrations.
- Performance improvements.
- Accessibility improvements.
- Security improvements submitted through the appropriate process.
- Community support and review.

Not every repository accepts every type of contribution.

## Before opening a pull request

Contributors should:

- Review the repository README.
- Read `CONTRIBUTING.md`.
- Search existing issues and pull requests.
- Review the project's current lifecycle and support status.
- Confirm that the proposed change is within project scope.

For significant changes, contributors should generally open an issue or discussion before beginning implementation.

This helps establish alignment before substantial work is performed.

## Pull requests

A good pull request should:

- Have a clear title.
- Explain what is changing.
- Explain why the change is needed.
- Reference related issues.
- Include tests where appropriate.
- Include documentation where appropriate.
- Keep unrelated changes separate.
- Pass required automated checks.

Maintainers may ask contributors to modify, split, or rework a pull request before it can be accepted.

## Review does not guarantee acceptance

Opening a contribution does not guarantee that it will be merged.

A contribution may be declined because it:

- Falls outside project scope.
- Conflicts with the project's technical direction.
- Creates disproportionate maintenance cost.
- Introduces compatibility concerns.
- Duplicates existing functionality.
- Belongs more appropriately in an upstream project.
- Does not meet security, testing, or quality expectations.
- Cannot be sustainably maintained.

Where practical, maintainers should explain why a contribution is declined.

## Contributor access

External contributors should normally contribute through forks and pull requests.

Direct write access should only be granted when there is a clear ongoing project need.

Access decisions should consider:

- Demonstrated project participation.
- Need for elevated permissions.
- Maintainer sponsorship.
- Security implications.
- Least-privilege principles.

Contributor access should be periodically reviewed.

Direct repository access is not required to participate meaningfully in a Dynatrace open source project.

## Becoming a maintainer

Some projects may allow long-term contributors to become maintainers.

Maintainer selection should be based on factors such as:

- Sustained contribution history.
- Technical knowledge.
- Constructive collaboration.
- Understanding of project goals.
- Reliability.
- Ability to review contributions.
- Commitment to the project's community and code of conduct.

Maintainer access should be documented and should follow the repository's governance model.

## Contribution agreements

Some repositories may require contributors to:

- Sign a Contributor License Agreement (CLA).
- Certify contributions under a Developer Certificate of Origin (DCO).
- Use signed commits or another repository-specific mechanism.

The repository's `CONTRIBUTING.md` should clearly state any requirement before contributors invest significant effort.

## Licensing

Unless otherwise documented, accepted contributions become part of the project under the repository's existing license.

Contributors are responsible for ensuring that they have the right to submit their contribution.

Do not submit:

- Proprietary code without authorization.
- Confidential information.
- Code copied from incompatible sources.
- Customer data.
- Credentials.
- Material that violates third-party intellectual property rights.

## Security vulnerabilities

Security vulnerabilities should not be reported through public GitHub Issues, Discussions, or pull requests.

Follow the reporting process described in the repository's `SECURITY.md`.

If a vulnerability is discovered while developing a contribution, use the security reporting process before publicly submitting the affected change.

## Community-supported repositories

Community-supported repositories may have different response expectations than officially supported projects.

Community-supported means:

- Contributions are welcome.
- Maintainers may review issues and pull requests as capacity allows.
- Response times are not guaranteed.
- Dynatrace Support does not provide formal product support unless explicitly documented.

See [Support Models](../governance/support-models.md).

## Experimental repositories

Experimental repositories may change rapidly and may not provide:

- Compatibility guarantees.
- Stable APIs.
- Long-term maintenance.
- Formal support.
- Regular release schedules.

Contributors should review the repository's status before depending on experimental projects in production environments.

## Code of Conduct

Contributors are expected to participate respectfully and constructively.

Harassment, discrimination, threats, or other behavior that violates the project's Code of Conduct is not acceptable.

Maintainers may restrict participation when necessary to protect the project and its community.

## Recognition

Where appropriate, external contributors should receive visible credit through Git history, release notes, acknowledgments, or other normal open source mechanisms.

Dynatrace should not remove contributor attribution when incorporating legitimate community contributions.
